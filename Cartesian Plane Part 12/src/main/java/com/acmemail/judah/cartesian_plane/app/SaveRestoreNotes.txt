❯ should we add to CommandProcessor a facility similar to Plotter/DefaultPlotter for handling OPEN/SAVE?

● Short answer: I'd lean no for OPEN, possibly yes for SAVE — but for a different reason than the Plotter pattern
  suggests.

  Why the Plotter pattern fits poorly for OPEN

  Plotter works because the call is fire-and-forget: CommandProcessor hands the renderer a stream, the renderer does
  whatever, no information flows back. OPEN is the opposite — it produces a new equation that has to replace the one the
   processor is bound to. Three ways to express that:

  1. Mutate equation — would require making the final field mutable. The whole class is currently designed around one
  processor / one equation; changing that propagates everywhere (newEquation() exists because the equation field is
  final).
  2. Return a richer Result — e.g. Result<Equation> that can signal "switch equation." Doable, but it's a contract
  change to a public type with a lot of callers.
  3. Keep the dispatch outside — exactly what CommandExecutorV2 does today: catches OPEN, calls the chooser, builds a
  new processor with new CommandProcessor(newEq, plotter).

  (3) is the path of least resistance and is already working. The "CommandProcessor owns one equation" invariant is
  load-bearing.

  SAVE is cleaner — but doing only SAVE is worse than doing neither

  SAVE is fire-and-forget at the processor level: take the current equation, hand it to something that writes bytes,
  merge a Result. That maps onto a Plotter-style interface fine:

  interface EquationStore { Result save(Equation eq, String name); }

  But pulling only SAVE inside while OPEN stays in the executor would make the asymmetry worse, not better. A reader
  hitting OPEN in V2 and SAVE in CommandProcessor would (rightly) wonder why.

  The better refactor — if there's appetite

  The thing V2 does that is worth abstracting isn't "OPEN/SAVE in CommandProcessor" but "the file-vs-chooser branch
  logic." V2's open() and save() each have a name.isBlank() switch between direct file I/O and the chooser. That pair of
   branches could move into a single EquationStore interface that the executor (not the processor) consumes:

  interface EquationStore {
      Optional<Equation> open(String name);    // empty name → chooser
      Result save(Equation eq, String name);   // empty name → chooser
  }

  DefaultEquationStore wraps FileManager + IEquationFileChooser + MessageConsumer. V2 shrinks dramatically (no more
  open()/save() private methods, just two store.open(...) / store.save(...) calls). Tests get a clean fake.
  CommandProcessor stays untouched.

  Recommendation

  - Don't pull OPEN/SAVE into CommandProcessor. The equation-replacement problem makes OPEN a poor fit, and
  inconsistency would be worse than the status quo.
  - Consider an EquationStore for the executor if V2 gets reused or if a V3 emerges. Right now it's a "yes, but no rush"
   — the current V2 code works and you've just finished testing it.

● EquationStore sketch + what V2 becomes

  The interface

  package com.acmemail.judah.cartesian_plane.input;

  import java.util.Optional;

  /**
   * Read/write operations for {@link Equation} files. Both operations
   * accept either an explicit file name or a blank string; blank means
   * prompt the user. On failure (cancellation, I/O error, parse error)
   * the operation returns an absent / false result and posts a message
   * to the configured {@link MessageConsumer}.
   */
  public interface EquationStore
  {
      /**
       * @param name explicit file path, or blank to prompt the user
       * @return loaded equation, or empty on cancellation/failure
       */
      Optional<Equation> open( String name );

      /**
       * @param equation equation to save
       * @param name     explicit file path, or blank to prompt the user
       * @return true if the equation was written; false on cancellation/failure
       */
      boolean save( Equation equation, String name );

      /** Sets the consumer used to report errors. Null restores default. */
      void setMessageConsumer( MessageConsumer consumer );
  }

  Two methods + a consumer setter. Mirrors IEquationFileChooser deliberately so the parallel is obvious.

  The default implementation

  package com.acmemail.judah.cartesian_plane.input;

  import java.io.File;
  import java.io.IOException;
  import java.util.List;
  import java.util.Objects;
  import java.util.Optional;

  import javax.swing.JOptionPane;

  public class DefaultEquationStore implements EquationStore
  {
      private static final MessageConsumer defaultConsumer =
          JOptionPane::showMessageDialog;
      private static final String          titleSave    = "Equation not saved";
      private static final String          titleStore   = "Equation Store";
      private static final String          newl         = System.lineSeparator();

      private IEquationFileChooser chooser;
      private MessageConsumer      messageConsumer = defaultConsumer;

      public DefaultEquationStore() { this( null ); }

      public DefaultEquationStore( IEquationFileChooser chooser )
      {
          setChooser( chooser );
      }

      public void setChooser( IEquationFileChooser chooser )
      {
          this.chooser = chooser != null ? chooser : new EquationFileChooser();
          this.chooser.setMessageConsumer( messageConsumer );
      }

      public IEquationFileChooser getChooser() { return chooser; }

      @Override
      public void setMessageConsumer( MessageConsumer consumer )
      {
          messageConsumer = consumer != null ? consumer : defaultConsumer;
          chooser.setMessageConsumer( messageConsumer );
      }

      @Override
      public Optional<Equation> open( String name )
      {
          Objects.requireNonNull( name, "name" );
          if ( name.isBlank() )
              return chooser.openDialog();

          Equation eq   = new Exp4jEquation();
          File     file = new File( name );
          try
          {
              Result result = FileManager.load( file, eq );
              if ( !result.success() )
              {
                  report( result );
                  return Optional.empty();
              }
              return Optional.of( eq );
          }
          catch ( IOException exc )
          {
              report( exc.getMessage() );
              return Optional.empty();
          }
      }

      @Override
      public boolean save( Equation equation, String name )
      {
          Objects.requireNonNull( name, "name" );
          if ( name.isBlank() )
          {
              boolean ok = chooser.saveDialog( equation );
              if ( !ok )
                  report( titleSave );
              return ok;
          }

          File file = new File( name );
          try
          {
              FileManager.save( file, equation );
              return true;
          }
          catch ( IOException exc )
          {
              report( exc.getMessage() );
              return false;
          }
      }

      private void report( String msg )
      {
          messageConsumer.postMessage(
              null, msg, titleStore, JOptionPane.INFORMATION_MESSAGE );
      }

      private void report( Result result )
      {
          List<String> msgs = result.messages();
          String joined = msgs.isEmpty()
              ? "Unexpected error; failed Result with no message."
              : String.join( newl, msgs );
          report( joined );
      }
  }

  What V2 looks like after

  The two private methods (open / save) disappear, along with the chooser field and its accessors. The exec() switch
  becomes:

  case OPEN -> {
      Optional<Equation> loaded =
          store.open( parsedCommand.getArgString() );
      if ( loaded.isPresent() )
          cmdProc = new CommandProcessor( loaded.get(), plotter );
  }
  case SAVE ->
      store.save( cmdProc.getEquation(), parsedCommand.getArgString() );

  The class shrinks meaningfully. Before / after at a glance:

  Tests

  V2Test's TFileChooser becomes a thin shim around a real DefaultEquationStore constructed with it — or a TEquationStore
   that's even simpler:

  private static class TEquationStore implements EquationStore
  {
      Optional<Equation> openResult = Optional.empty();
      boolean            saveResult = false;
      MessageConsumer    consumer;

      @Override public Optional<Equation> open(String n) { return openResult; }
      @Override public boolean save(Equation e, String n) { return saveResult; }
      @Override public void setMessageConsumer(MessageConsumer c) { consumer = c; }
  }

  That's it. The "name vs blank" branching, the "FileManager vs chooser" branching — none of it has to be re-stubbed in
  the test. The test isolates V2 from the file system entirely.

  Trade-offs and decisions to make

  1. open() swallows error context. Returning Optional means V2's exec() can't distinguish "user cancelled" from "I/O
  error." For the current behavior (messages go through MessageConsumer, V2 doesn't care why) that's fine. If you ever
  want to react differently — e.g. only retry on I/O error — you'd want a Result<Equation> or a sealed result type.
  2. The store owns the chooser. That means setEquationFileChooser is no longer on V2; callers reach the chooser via
  getStore().setChooser(...). Cleaner separation, but a public API change. If you want to soften the migration, V2 could
   keep a setEquationFileChooser shim that delegates.
  3. Same trick as Plotter — no graphics dependencies in the interface. EquationStore lives in input, talks in
  Equation/Optional/String. DefaultEquationStore is also in input because all its dependencies (FileManager,
  EquationFileChooser, etc.) live there. Unlike Plotter/DefaultPlotter — which had to split across packages — these two
  can co-locate.
  4. Exp4jEquation reference in DefaultEquationStore.open() is the same coupling V2 has today. If you ever want store to
   be Exp4j-agnostic, push that allocation behind a factory. Not urgent.

  Recommendation

  This refactor is moderate effort, high readability win. V2 stops being a class about "file handling + plotting +
  dispatch" and becomes "the dispatch loop, with two collaborators it doesn't peek inside." That's worth doing if V2 is
  the long-term shape; if you expect V2 to keep evolving toward V3 with more responsibilities, doing the extraction now
  makes V3 easier to design.
